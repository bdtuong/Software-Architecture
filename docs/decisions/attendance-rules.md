# Attendance decisions for M2

The M1 report left event qualification, entry/exit interpretation, corrections, and late-event reconciliation open. The following decisions are implementation assumptions for the assignment; TMC stakeholders would validate them before production use.

1. **Qualified event contract.** Gate Service emits an event only after a supported physical-passage signal. It supplies a stable Event ID, unique passage-evidence reference, factory, gate, employee, direction, and occurrence timestamp. Attendance Service verifies the signed gateway identity and factory scope, validates the shape, and enforces unique identifiers. It cannot independently inspect the real turnstile signal because the controller contract is unspecified. An Allow decision or accepted gate command is insufficient.
2. **Authoritative record and idempotency.** The raw attendance event is immutable. PostgreSQL commits the event, Event ID, monthly-period invalidation, and audit outbox entry in one central transaction. An identical retry returns the original record; changed content with the same Event ID or evidence ID is an error. The Factory Edge SQLite outbox remains a separate Gate Service responsibility. The central service never claims delivery before commit.
3. **Time and state.** `occurredAt` is the source of chronology, not arrival time. Effective history applies approved ADD, REPLACE, and VOID corrections without modifying raw events. The latest effective ENTRY means `IN`, EXIT means `OUT`, and no entry means `UNKNOWN`. Consecutive equal directions are retained and flagged `requiresReview`; future timestamps beyond two minutes of clock skew are rejected; no automatic missing, late, overtime, or shift classification is invented without a shift roster and agreed policy.
4. **Corrections.** Employees request corrections only for themselves; authorized security guards may request for employees within their factory. HR staff review within their factory. A requester cannot approve their own request; admins have no implicit HR approval power. A target event can have only one approved REPLACE or VOID correction. ADD represents a verified missing transaction. Approval is final and auditable; subsequent mistakes require a new controlled process, not silent mutation.
5. **Monthly reconciliation.** Months use `Asia/Ho_Chi_Minh` calendar boundaries. HR manually finalizes a completed month per factory after all pending corrections for that period have been reviewed. Integration Service can export only a finalized revision. A later event or approved correction touching that month changes it to `REOPEN_REQUIRED`; HR reviews and finalizes a new revision before another export. This prevents silent changes to previously exported data. The Integration Service still owns external HR/Payroll transmission, acceptance, and reconciliation status.
6. **Audit and privacy.** Event acceptance, correction request/review, and period finalization write audit messages in the same PostgreSQL transaction as the domain change. Reporting and Audit Service polls and acknowledges messages only after its own durable storage; it deduplicates by outbox message ID. Tokens carry role, factory, and employee scope. Employee-facing history enforces resource-level access. Production deployment still needs TLS, identity issuance, key rotation, retention policy, backup/restore, and PostgreSQL high availability.

## M1 boundary retained

Identity and Access Service issues trusted identities and performs QR authorization. Gate Service owns scanner, turnstile, event qualification, and factory-local SQLite outbox. Attendance Service owns central records, effective state, corrections, and period finalization. Reporting and Audit Service owns searchable audit logs and reports. Integration Service owns HR/Payroll transfer and reconciliation. This repository implements only Attendance Service plus its inbound/outbound contracts.
